# Interface localisation

The Switch port's UI is written in English as C++ string literals. This document
describes how those strings get translated at run time, and what has to be in
place for a new language.

## Why the keys are the English text

RmlUi renders a text node by calling `SystemInterface::TranslateString`. The
port sets the node's text directly (`set_text_content`, `add_text`, `.key = …`),
so what arrives at that call is the finished English sentence.

That means the dictionary key can be **the English sentence itself**:

```xml
<entry key="Adjusts the volume of all music in the game.">调节游戏中所有音乐的音量。</entry>
```

and no call site has to be touched. This matters because the port moves: a
tokenised UI would conflict on every upstream merge, while a dictionary keyed on
source text never does. A string that is not listed simply stays English.

Two lookup passes run before the `[TOKEN]` substitution the dictionary also
supports:

1. the whole trimmed string, for ordinary labels and help text;
2. the first line of a multi-line block, so `"Enabled Mods:\n<list>"` translates
   its header and keeps the list.

## What has to be in place

| Piece | Where | Why |
|---|---|---|
| Translate hook | `ci/patches/aurora-translate-callback.py` | aurora does not override `TranslateString`, so there is nowhere to hook. 26 lines, applied at configure time, no-op when already applied. |
| Engine | `src/dusk/ui/i18n.cpp` | Loads `<language>.xml`, parses it, answers the callback. |
| Setting | `settings.h` → `ui.language` | Which file to load; default `en`. |
| Font | `res/HarmonyOS_Sans_Regular.ttf` | None of the bundled faces carry a Han codepoint, so Chinese would rasterise as blanks. Loaded as a fallback so Latin text keeps FiraSans' metrics. |
| Text | `res/i18n/en.xml`, `res/i18n/zh-cn.xml` | Shipped in romfs, because `platforms/switch/CMakeLists.txt` copies all of `res/`. |

## Adding or updating a language

```sh
# 1. Re-extract the strings the port currently renders (joined literals, comments stripped)
python tools/extract-ui-strings.py . ci/i18n/source-strings.json

# 2. Translate what is new. Existing entries are kept; missing ones fall back to English.
#    ci/i18n/zh-cn.json is the translation map: English source text -> target text.

# 3. Rebuild the shipped dictionaries
python tools/build-i18n.py ci/i18n/source-strings.json ci/i18n/zh-cn.json res/i18n
```

`build-i18n.py` writes `en.xml` as an identity map (key = value), which is what
makes a partially translated language degrade line by line instead of blanking
out. It refuses nothing: a key with no translation is emitted with the English
text as its value.

### Coverage

`ci/i18n/source-strings.json` currently holds **1586** rendered literals.
`ci/i18n/zh-cn.json` translates **1388** of them; the remaining 198 are listed in
`ci/i18n/not-translated.txt` on purpose:

| Group | Count | Why it stays English |
|---|---|---|
| Wire format and constants | 27 | HTTP/WebSocket field names, ELF relocation names, format strings — translating them breaks the protocol or the format |
| Assembled fragments | 28 | Pieces the loader concatenates; the callback sees the finished sentence, which never equals the fragment |
| Loader internals | 143 | ELF/TLS diagnostics that go to the log, or get appended to a sentence that then stops matching as a whole |

A translated entry is only worth adding when the finished string reaches
`TranslateString` intact. Everything else is noise in the dictionary.

To add a third language, translate the same source strings into a new map, emit
`res/i18n/<code>.xml`, and add the code to `kLanguages` in
`src/dusk/ui/settings.cpp` *and* the accepted list in `i18n::set_language`.
A code with no file falls back to English at load time.

## Switching language

Settings → the interface section → **Language**. The value is persisted as
`ui.language`; text already on screen keeps its language until the screen is
rebuilt, which is why the picker says the change takes effect at the next start.

## Known limits

- Dynamically formatted strings (`fmt::format`) are not in the dictionary: the
  callback sees `"Frame rate: 59"`, which is not the literal in the source. Those
  need a pattern entry or a source change if they are worth translating.
- RML blocks passed to `add_rml` are split into several text nodes by the parser,
  so only whole-node runs translate. Most long help text is written with
  `add_rml`, and it stays English until it is moved to `add_text` or its runs are
  added individually.
- The dictionary is compiled into romfs; romfs is read-only, so a language pack
  cannot be dropped on the SD card at run time.
